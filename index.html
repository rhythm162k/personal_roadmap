What I’m building

A service request → completed job workflow

The first target is a small AC repair, appliance repair or home-maintenance business. The product is a configurable web app, not a general-purpose CRM or a full field-service suite.

The customer journey

I publish the business’s services, service area and contact details.
A customer submits a request, describes the issue and optionally uploads photos.
The owner reviews the request, creates a simple quote, chooses a time and assigns a technician.
The technician sees assigned jobs on a phone and updates progress.
The customer follows a secure status link and sees the approved quote and payment status.
The business records a cash, bank-transfer or mobile-financial-service payment.

Sellable first release

  • Public service list and service request form.
  • Business dashboard for requests, customers, jobs and assignments.
  • Technician-friendly mobile job view.
  • Scheduling with database-level double-booking prevention.
  • Simple quote and manual payment records.
  • Customer tracking with a secure, expiring link or authenticated access.
  • Email notifications for key status changes.
  • One configurable business first; a second business type as a re-skin test.

Architecture decisions to defend

  • Modular monolith first; no premature microservices.
  • Every tenant-owned record carries a business boundary; enforce it in database policies and server authorization.
  • Job status changes follow an explicit state machine and create an audit event.
  • PostgreSQL prevents overlapping technician bookings, not just the calendar UI.
  • Money is stored as integer minor units; totals are calculated on the server.
  • Notifications run asynchronously and are safe to retry.
Not part of the 50-day MVP Native mobile apps, GPS tracking, route optimisation, automatic dispatch, recurring subscriptions, real payment-gateway settlement, self-serve SaaS onboarding and multi-region infrastructure. I can add these only after a pilot proves the need.
AI feature blueprint

A service assistant that helps customers take the next step

The chatbot is not a generic ChatGPT window. It should reduce repetitive questions, help customers describe a problem, and turn a conversation into a structured service request. I’ll add it after the core request-to-job workflow is reliable.

Where it helps in this product

  • Answer business-specific questions: services, opening hours, service areas, pricing rules, preparation and warranty policies.
  • Ask guided questions about the issue and suggest the right service category.
  • Check whether the business serves an address or area.
  • Check available appointment windows without promising a booking.
  • Prepare a service-request draft from the conversation for customer confirmation.
  • Hand off unclear, urgent or sensitive cases to a human.
  • Later, authenticated customers can ask for the status of their own request.

What RAG and MCP each do

RAG = trusted business knowledge. I retrieve relevant chunks from service descriptions, FAQs, coverage areas, opening hours, policies and preparation guides. The model answers from those sources and says when the information is missing.

MCP = controlled actions and live data. I expose a small set of typed tools, such as listing services, checking service coverage, finding available slots, creating a request draft and retrieving an authenticated customer’s request status.

They work together. RAG explains the business’s rules; MCP reads current system data or performs an explicitly permitted action.

Architecture I intend to build

Chat widget sends messages to my own backend endpoint. No model API key or MCP credential is exposed in the browser.
Chat orchestration service applies rate limits, identifies the business from trusted server-side context, calls the model provider and keeps a short conversation history. My backend acts as the MCP host/client: it passes approved tool schemas to the model, validates a proposed tool call and then invokes the MCP server. The model never connects to the database or MCP server directly.
RAG retrieval embeds the question, searches business-scoped knowledge chunks in PostgreSQL + pgvector and returns source snippets.
MCP tool server exposes only allowlisted, typed tools. Each tool calls existing application services; it never accepts arbitrary SQL or trusts a business_id supplied by the model.
Existing application services enforce tenant access, customer identity, validation, availability and audit logging exactly as they do for normal API requests.
Confirmation and handoff show the proposed request or appointment details before submission; consequential actions require customer confirmation or owner approval.

First chatbot slice

  1. Store business FAQs and service information as versioned knowledge documents.
  2. Chunk, embed and store them with business_id metadata in pgvector.
  3. Retrieve only chunks belonging to the active business.
  4. Answer FAQs with source-grounded responses and a clear fallback.
  5. Expose read-only MCP tools: list services, check service area and inspect available slots.
  6. Add a create-request-draft tool, then require a clear confirmation before submission.

Safety and evaluation I won’t skip

  • Never let the model invent a quote, availability or policy.
  • Never let it access arbitrary database queries or another business’s records.
  • Derive tenant and customer identity from trusted backend authentication, not chat text.
  • Require confirmation before creating a request or booking.
  • Treat uploaded documents and retrieved text as untrusted input; test prompt injection.
  • Build a small evaluation set: correct FAQ answers, missing-answer cases, tool selection, tenant isolation and refusal/handoff cases.
  • Log tool calls and outcomes without unnecessarily retaining sensitive conversation data.
Scope decision I will not make the chatbot a launch blocker. The first useful version is FAQ retrieval plus guided service triage. Live availability and request creation through MCP come next, once the underlying scheduling and request APIs are tested. Authenticated request tracking is a later addition.
Learning order

RAG first, tools second, evaluation throughout

1 · LLM application basics

Model/API calls, structured outputs, token and latency costs, prompt design, provider adapter, server-side secrets and rate limits.

2 · RAG foundations

Document ingestion, chunking, embeddings, vector similarity, metadata filters, retrieval quality, citations and update/delete handling.

3 · MCP and tool calling

Resources vs tools, JSON schemas, TypeScript MCP SDK, tool validation, authorization, timeouts, retries and confirmation boundaries.

4 · Production quality

Evaluation dataset, prompt-injection tests, cross-tenant tests, tracing, cost/latency monitoring, fallback and human handoff.

Real client work

Find a pilot while I build

Customer discovery

  • Speak with at least two AC repair, appliance repair or maintenance business owners.
  • Ask how requests arrive, how jobs are assigned, how schedules change and how payments are recorded.
  • Ask to see the current process; do not pitch features before understanding the workflow.
  • Write down the three most expensive or frustrating problems.
  • Confirm whether a web dashboard and mobile technician page would fit the real operation.

Pilot approach

  • Show a working flow on a phone and laptop, not only screenshots.
  • Offer a tightly scoped, low-cost pilot if useful, with clear duration and support boundaries.
  • Use synthetic data until hosting, access, backups and privacy are ready.
  • Get written permission before using a business name, logo, customer data or testimonial.
  • Measure onboarding time, requests processed and issues fixed; never invent CV metrics.
If no business agrees to a pilot by the final week I will still finish a realistic demo with seeded data, ask two owners to review it, record their feedback and keep outreach active. A pilot is a goal, not a guaranteed outcome.

Where I’ll look

  • Direct outreach to local repair, cleaning and maintenance businesses.
  • Upwork, Freelancer and PeoplePerHour listings to learn recurring client requirements.
  • LinkedIn to reach owners, operators and founders.
  • My own network for a first design partner and warm introduction.

A demo and a real conversation are more useful than assuming that every business needs the same workflow.

AWS without surprise bills

  • I verify current account eligibility, pricing and credit expiry before creating resources.
  • I enable MFA and billing alerts first, use least-privilege IAM and avoid daily root use.
  • I practise a small EC2 + Docker deployment, then S3 object storage and HTTPS delivery if the budget permits.
  • I tear down billable lab resources after each exercise and verify that they are actually deleted.
  • I use a managed platform for the pilot if AWS costs or operational risk are not justified.

Redis and performance without cargo culting

  • I use Redis first where it solves a real queue/rate-limit need.
  • I measure dashboard queries with EXPLAIN ANALYZE and realistic seed data.
  • I add cache-aside only after identifying a repeated expensive read.
  • I define TTL and invalidation rules, then test stale-data behaviour.
  • I record before/after latency rather than claiming an unmeasured speed-up.
My engineering habits I design the schema and API contracts before asking AI to draft code. AI helps with research, implementation drafts and test ideas; it does not replace understanding.
