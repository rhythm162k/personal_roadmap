What I'm building

One store engine, many shops

The idea

One codebase. Each shop is a config: theme, product attributes, delivery zones, languages, payment options. Selling to the next shop means writing a config and importing products, not forking the code.

React + TypeScriptNode + ExpressPostgreSQL + RLSDrizzleRedis + BullMQpgvectorDockerAWS

MY guess is mostly right

Checkout, orders, stock and delivery really are the same everywhere. What differs is the product itself. That's why attributes are stored per store as JSONB, validated by a schema in the store config.

What changes per shop type

Shop Variant attributes Special flows
Jersey Size, fan or player version Name + number printing, pre-orders, limited stock
Clothing Size, colour Exchange policy, size guide
Eyewear Frame colour, lens type Prescription details, warranty, try-on questions
All of them Catalog, cart, guest checkout, COD, order lifecycle, delivery zones, invoices, chatbot

Sellable MVP

  • Merchant manages products, variants, stock and orders.
  • Guest checkout with phone number first; no account needed.
  • Cash on delivery by default, manual bKash/Nagad TrxID next.
  • Delivery fee by district or zone.
  • Bangla and English, fast on slow mobile data.
  • Order lifecycle with an audit trail.
  • Fake-COD signals: repeat numbers, many cancellations.
  • Chatbot for product, policy and order questions.

Decisions to explain in interviews

  • Modular monolith, not microservices.
  • store_id on every tenant table, enforced by RLS.
  • Server computes prices; never trust the client.
  • One transaction for order + stock; idempotency keys.
  • Payments and couriers behind provider interfaces.
  • Background jobs for email, imports, notifications.
  • Write each choice down as a short ADR.

Advanced feature track

An assistant that knows the shop

RAG, tools and MCP solve different problems.RAG finds relevant text (policies, FAQs, guides). Tools fetch live facts (stock, price, order status). MCP is a standard way to expose those tools to AI clients. Never answer live stock or order status from embeddings; they go stale.

RAG: knowledge

  • Shipping, returns, exchange, size and care guides.
  • Chunk, embed, store in pgvector, retrieve top-k.
  • Show the source; say "I don't know" when retrieval is weak.
  • Store the embedding model name and dimension with each row.

Where MCP actually earns its place

For the customer chat inside MY site, plain function calling to MY own service is simpler. MCP shines when an outside client connects to MY tools. So give MCP a real job: a merchant connects Claude (or another MCP client) and asks "how many orders are pending today?" Authenticated, read-only, one store.

Free LLMs: plan for change

Free API tiers keep shrinking, and some allow MY prompts to be used for training. Use them with fake demo data only. Put the model behind one adapter so I can switch between a hosted model, a local one through Ollama, or the client's paid key. Real customer data belongs on a paid tier, and LLM cost goes into MY price.

Security ruleThe backend decides who may see an order, never the model. Treat user messages and retrieved documents as untrusted. No raw SQL access, no write tools without a human confirming. Test prompt injection, "show me someone else's order", and "say the jersey is free" before every release.
Free tier, honestly

AWS & a SPOF-proof path

The free plan is shorter than most tutorials say.New accounts get up to $200 in credits, but the free plan ends after 6 months or when credits run out, whichever comes first, and the account then closes unless I upgrade. Guides promising "12 months free" describe the old system. Open MY account in Week 3, not earlier, and read MY own end date on the Credits page in Billing.

Cost rules

  • Budget alert and MFA before anything else; never use root day to day.
  • Load balancers and NAT gateways bill by the hour. Run labs for a day, then delete.
  • Some services are restricted on the free plan; check each one on the Free Tier page.
  • Run Redis in a container on MY instance. Managed Redis costs money.
  • Don't host a paying client on credits that expire. Price hosting into the offer.

Custom domain, end to end

  • Buy or borrow a domain (the registration is the only unavoidable cost).
  • Point nameservers to Cloudflare (free DNS) or Route 53 (small monthly fee).
  • Request a free ACM certificate.
  • Add DNS records for the app and CloudFront.
  • Force HTTPS and test with curl and browser devtools.
Deploy ladder

Climb it as money allows

Level 0 · Week 3: one instance, Docker Compose

Cheapest, and everything is a single point of failure. Fine for learning and a pilot.

Level 1 · Week 6: managed pieces

RDS with backups and a tested restore, S3 + CloudFront, ACM HTTPS, CD with OIDC, alarms.

Level 2 · Week 8 labs: no single AZ or instance

Load balancer, two instances in two AZs, RDS Multi-AZ, then ECS Fargate. Short, torn-down labs.

Level 3 · when a customer pays

Autoscaling, read replica, WAF, Terraform, blue/green deploys, a written disaster-recovery runbook with real RTO and RPO.

AI-era engineer

Six rules

  • Design first, prompt second. Schema, API contracts and state machines are MYs; AI drafts around them.
  • Explain-back before ticking. Answer each week's question out loud. If I stall, I don't own it yet.
  • Read every diff. Small PRs even solo; never merge what I can't explain.
  • I write the test cases; AI helps type them. Break the code on purpose to watch them fail.
  • Write ADRs. One paragraph per decision in docs/decisions. They become MY interview stories.
  • Keep a confusion log. Each Friday, turn the top three into videos to watch.
